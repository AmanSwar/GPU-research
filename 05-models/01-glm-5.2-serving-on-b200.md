### Naming footgun: IndexShare vs IndexCache

The model card calls the feature **IndexShare** and links it to arXiv 2603.12201.
That paper is titled **IndexCache** and never uses the word "IndexShare". `[verified]`
SGLang uses both names in different files. TensorRT-LLM's PR calls it "cross-layer indexer
top-k sharing". They are the same mechanism. Search for all three.

Read that table as a trajectory:

1. **GLM-4.5 -> 4.6** is a context bump on an unchanged dense-attention MoE.
2. **4.6 -> GLM-5** is the architectural break: 92 shallow-wide GQA layers become 78 layers
   of MLA + DeepSeek Sparse Attention, and the expert count goes 160 -> 256.
3. **GLM-5 -> GLM-5.1** is, at the config level, **nothing**. Every key I compared is
   identical. `[verified]` Whatever 5.1 is, it is a re-training, not a re-architecting.
4. **GLM-5.1 -> GLM-5.2** is **exactly three changes**: `index_topk_freq` 1 -> 4 (plus the

   `indexer_rope_interleave`, `rope_interleave` fields that come with it), context
   202752 -> 1048576, and `rope_theta` 1e6 -> 8e6. `[verified]`

**That is the whole story of why GLM-5.2 is cheaper than GLM-5**: it is GLM-5.1 with 57 of
its 78 lightning indexers deleted and the context extended 5.2x on plain RoPE.

### Parameter count: 744B or 753B?

Both circulate. `[reported]` `github.com/zai-org/GLM-5` README says **744B total / 40B
active** for GLM-5, GLM-5.1 *and* GLM-5.2. `[reported]` the `zai-org/GLM-5.2` card and the
`nvidia/GLM-5.2-NVFP4` card say **753B in total and 40B activated**.
`[verified]` the checkpoints on this box hold exactly **753,329,921,024** parameters.

`[inferred]` The gap is the MTP layer. Layer 78 is a complete decoder layer:

```
256 experts x 3 x 6144 x 2048            = 9,663,676,416
shared expert 3 x 6144 x 2048            =    37,748,736
attention (same as any layer)            =   165,019,648
indexer                                  =     9,371,648
router 256 x 6144                        =     1,572,864
eh_proj 6144 x 12288                     =    75,497,472
norms (enorm/hnorm/shared_head.norm/...) =        ~30,000
                                           --------------
                                            9,952,916,784   = 9.95 B

753,329,921,024 - 9,952,916,784 = 743,377,004,240  ~= 744 B
```

So **744B = the target model without the draft head; 753B = with it.** Quote 753B when
you are sizing HBM, 744B when you are comparing against a published 744B figure.

## What this is

GLM-5.2 is a 753B-total / 40.3B-activated Mixture-of-Experts decoder with DeepSeek-style
MLA latent attention, DeepSeek Sparse Attention (a "lightning indexer" that selects
top-2048 keys per query), 256 routed experts at top-8 plus one always-on shared expert,
three leading dense layers, one in-checkpoint MTP layer, a 1M-token context on unscaled
RoPE, and a **default reasoning effort of "max"**.

Two things make it structurally different from DeepSeek-V3.2 / Kimi K2, and both matter
for serving:

- **IndexShare.** Only 21 of 78 layers own an indexer. The other 57 reuse the nearest
  preceding full layer's top-k. This is the cost win and it is also why two-batch overlap
  is refused.
- **The reasoning volume.** At default effort, most generated tokens are thinking tokens.
  Every latency metric you publish has to say whether it counts them.

`[verified]` from `/home/aman/code/NotSglang/python/sglang/srt/models/glm4_moe.py:1466`,
SGLang has **no GLM-5.2 decoder layer**. `GlmMoeDsaForCausalLM` subclasses
`DeepseekV2ForCausalLM` and overrides one method. Every kernel in a GLM-5.2 profile is a
DeepSeek-V2/V3 kernel.

## Bottom line for serving it on 8xB200

Ranked by expected value per unit of effort. Each item is expanded later.

### 1. Get EAGLE 5-1-6 working. It is the published, "verified" B200 config — you are running the fallback.

`[verified]` SGLang's own cookbook config for `{hw: b200, quant: nvfp4, strategy: low-latency}`
is `--speculative-num-steps 5 --speculative-eagle-topk 1 --speculative-num-draft-tokens 6`,
marked `verified: true`. `[verified]` 3-1-4 is not a recommendation — it is
`_auto_choose_speculative_params`' default for the whole DeepSeek/GLM family
(`arg_groups/speculative_hook.py:800-822`), i.e. what you get when you say nothing.

`[reported]` Published accept lengths for GLM-5.2 at **5-1-6** on `nvidia/GLM-5.2-NVFP4`
(SGLang PR #29787, TP4, temp 0, fp8 KV):

| dataset | out_len | accept length |
|---|---:|---:|
| mtbench | 771 | 3.66 |
| humaneval | 688 | 4.33 |
| gsm8k | 717 | 4.49 |
| math500 | 1630 | 4.61 |
| aime | 3899 | 4.63 |
| openhands_longctx | 503 | **5.18** |

`[inferred]` Our 2.74 ms TPOT at 3-1-4 implies an accept length near **2.1** (see §6.3).
Published 5-1-6 gets 4.6 on long-reasoning workloads. **The gap is roughly 2x, and this
is the single biggest number on the page.**

The crash is a known, open, unfixed upstream bug: **SGLang issue #31093**, "GLM-5.2 NVFP4 +
EAGLE: CUDA illegal memory access during decode CUDA-graph capture", 8xB200 TP8,
`--quantization modelopt_fp4`, opened 2026-07-14, still open. Three concrete things to try,
in order (§6.4).

### 2. Requantize the NVFP4 build's non-expert GEMMs. 31% of decode bytes are BF16 for no reason.

`[verified]` (ground-truth §5) the NVFP4 checkpoint quantizes **only** `model.layers.{3..77}.mlp.experts.*`.
All attention, all shared experts, the three dense layers, the indexers, the router and the
whole MTP layer are BF16 — *twice the size they are in the FP8 checkpoint*.

`[inferred]` (§3.2) at TP8, per rank per decoded token:

| build | bytes read / token / rank | HBM ceiling @ 8 TB/s |
|---|---:|---:|
| FP8 checkpoint | 6,674 MB | 1199 tok/s |
| **NVFP4 checkpoint as shipped** | **8,756 MB** | **914 tok/s** |
| NVFP4 with every non-expert GEMM at FP8 | 6,048 MB | 1323 tok/s |

**The "FP4" build reads 31% more bytes per token than the "FP8" build.** The single largest
BF16 item is `fused_qkv_a_proj_with_mqa` at **2,515 MB/token/rank (28.7%)** — and it is
`ReplicatedLinear`, so TP8 does not shrink it at all. SGLang's only escape hatch,
`SGLANG_NVFP4_CKPT_FP8_GEMM_IN_ATTN`, covers `q_b_proj` only: **3.7%**.

### 3. Delete the dead indexer KV cache. 12% of the KV budget is allocated for layers that never read it.

`[verified]` `DSATokenToKVPool._create_index_buffers` allocates one indexer-K buffer per
layer for all 78 layers; only 21 (+MTP) own an indexer. `[inferred]` 7,392 B/token/GPU
wasted = 12.0% of the 61,464 B/token FP8-KV cost.

`[reported]` TensorRT-LLM already fixed this: PR NVIDIA/TensorRT-LLM#16558, merged
2026-08-05, "Reduces Indexer-K cache accounting per token (55,224 -> 47,700 bytes/token),
increasing effective KV capacity by ~15.8%". The 7,524 B/token they save is
`57 shared layers x 132 B` — an exact independent confirmation of our 132 B/token/layer figure.
`[verified]` SGLang's equivalent, PR #30531, is **still open**.

### 4. Do not chase two-batch overlap. Upstream refuses it, and the refusal is correct.

`[verified]` upstream `server_args.py:5316-5328` (and our fork at `:5053-5063`) raises:

```
--enable-two-batch-overlap is not supported with DSA index-topk sharing
(index_topk_freq > 1 or an index_topk_pattern containing shared layers):
the TBO op path does not propagate topk indices across layers, so shared
layers would run sparse attention without indices.
```

This is a hard `raise ValueError`, not a warning. It fires on `index_topk_freq = 4`.
§1.3 characterises the tradeoff precisely.

### 5. Attack rank-arrival skew directly; it is 9.2% of TPOT and it is not a bandwidth problem.

Measured: collectives 19.6% of C1 time, 47% of that is rank-arrival skew =
**9.2% of TPOT**. `[inferred]` (§3.4) the *bandwidth* term for all 156 per-token
all-reduces is ~2 microseconds on NVLink5. The entire 537 microseconds is launch overhead,
fixed cost and waiting. Track SGLang PR **#34134** ("Integrate the CuTe DSL allreduce
fusion from FlashInfer and tune for GLM-5.2").

### 6. TileRT is not available to you for this model. Stop planning around it.

`[verified]` `tile-ai/TileRT` README: the weight converter takes `--model_type glm-5`, the
CLI takes `--model glm5`, and the shipped backend libraries are `libtilert_dsv32.so` and
`libtilert_glm5.so`. Every news item names **GLM-5 / GLM-5.1 / DeepSeek-V3.2**. There is no
GLM-5.2 path. `[verified]` `/home/aman/code/weights/GLM-5.2-FP8-TileRT/` is empty. §7.4.

### 7. Understand that the default reasoning effort is "max", and that only one alternative exists.

`[verified]` from `chat_template.jinja` line 2 (identical in both local builds):

```jinja
{%- set effective_reasoning_effort = 'high' if reasoning_effort is defined
    and reasoning_effort == 'high' else 'max' -%}
```

`reasoning_effort` is honoured for exactly one value. `"low"`, `"medium"`, `"none"`,
`"minimal"` and every typo silently become **max**. §6.6.

### 8. Skip building indexer modules on the 57 shared layers. ~1.07 GB/GPU of never-read weights.

`[reported]` SGLang PR #30922: "~18.7 MB/layer in bf16 ... all `ReplicatedLinear`, so the
waste is per-GPU and does not shard with TP (~1.07 GB bf16 / ~0.55 GB FP8 per GPU on
GLM-5.2)". Closed, not merged. TensorRT-LLM does build only on full layers (#15574).

### 1.2 The DSA implementation, in full

This is the part of GLM-5.2 that is not DeepSeek-V3.2, so it gets the most space.

**The lightning indexer, per full layer.** `[verified]` from the layer-10 tensor inventory:

```
indexer.wq_b          [4096, 2048]  q_lora(2048) -> 32 index heads x 128   ReplicatedLinear
indexer.wk            [ 128, 6144]  x -> ONE shared 128-d index key         ReplicatedLinear
indexer.weights_proj  [  32, 6144]  x -> per-head gate (32)                 ReplicatedLinear
indexer.k_norm        [128] + bias  LayerNorm (has a bias, so not RMSNorm)
```

`[verified]` On CUDA, `wk` and `weights_proj` are concatenated at load into one **BF16**
`wk_weights_proj [160, 6144]`, and if the checkpoint stored `wk` in block-FP8 it is
dequantized to BF16 to fill it (`deepseek_weight_loader.py:105-122`). **The FP8 build's
indexer therefore runs the same BF16 GEMM as the NVFP4 build's.**

`[inferred]` 9,371,648 params per indexer, **all replicated on every TP rank**. The whole
indexer stack is 21 x 9,371,648 = 196,804,608 params on every GPU. TP8 does not help.

**Top-k selection.** `index_topk = 2048`. The indexer scores every previous token against
the current query with 32 heads of dim 128, gates by `weights_proj`, and keeps the 2048
highest. `[verified]` The kernel path is `DSAPagedMQALogitsBackend` (`dsa_backend.py`) —
in a profile these appear as `cutedsl_paged_mqa_logits` and
`parseP1MultiCtasKvVarSeqQ8Kv128StaticSwapsAbForGen`. The indexer runs at `scale_fmt="ue8m0"`,
`block_size=128`.

**The freq-4 sharing rule — exactly.** `[verified]` two independent ways.

1. The config's own `indexer_types` array has `"full"` at layers
   `0, 1, 2, 6, 10, 14, 18, 22, 26, 30, 34, 38, 42, 46, 50, 54, 58, 62, 66, 70, 74`
   — 21 entries — and `"shared"` at the other 57.
2. The engine derives the identical set arithmetically without reading `indexer_types`.
   `[verified]` `model_config.py:170`:

```python
def dsa_layer_skips_topk(layer_id, freq, offset):
    return max(layer_id - offset + 1, 0) % freq != 0
# GLM-5.2: freq=4, offset=3  ->  max(layer_id - 2, 0) % 4 != 0
```

   `layer_id in {0,1,2}` -> `max(...) = 0` -> `0 % 4 == 0` -> does **not** skip -> **full**.
   `layer_id = 6` -> `4 % 4 == 0` -> full. `layer_id = 7` -> `5 % 4 = 1` -> shared.
   The three leading layers are full because the clamp at 0 makes them full, which is
   also the paper's rule ("The first layer is always F to seed the initial indices"
   `[reported]` arXiv 2603.12201).
3. The checkpoint agrees: `model.safetensors.index.json` contains `self_attn.indexer.*`
   tensors for exactly `{0,1,2,6,10,...,74}` **plus layer 78** (the MTP layer) —
   22 sets. `[verified]`

`[reported]` TensorRT-LLM implements the same resolution order and says so:
"`index_topk_pattern` > `index_topk_freq`/`index_skip_topk_offset`; MTP layer always full;
defaults to full. Like upstream, the checkpoint's `indexer_types` array is not read — for
GLM-5.2 the freq/offset fields reproduce it exactly (21 full / 57 shared)."
(NVIDIA/TensorRT-LLM#15574, merged 2026-07-01.)

**How the index travels.** `[verified]` `DeepseekV2Model.forward` (`deepseek_v2.py:2706`)
threads a `prev_topk_indices` tensor through the layer loop. Inside attention,
`should_run_indexer` (`forward_mla.py:173`) is
`not self.skip_topk or (is_nextn and prev_topk_indices is None)`. On a shared layer it is
False and the layer calls `maybe_capture_indexer_topk(layer_id, prev_topk_indices)` — it
forwards the carried tensor unchanged. **The top-k are token positions, which are
layer-agnostic; each layer then applies its own paged-KV transform to them.** `[reported]`
TRT-LLM #15574 states the same invariant.

**What IndexShare is worth.** `[reported]` the FP8 model card: "reuses the same indexer
across every four sparse attention layers, reducing per-token FLOPs by **2.9x** at a 1M
context length". `[reported]` the IndexCache paper, on a 30B DSA model at 200K context:
prefill 19.5 s -> 10.7 s (**1.82x**), per-request decode 58 -> 86 tok/s (**1.48x**),
full-KV decode 197 -> 297 tok/s (1.51x). On GLM-5 itself the paper reports "at least 1.3x
speedup with negligible degradation" and a Long-Avg of 78.0 at 1/4 retention vs 78.4 for
dense DSA.

**One caveat the paper raises and GLM-5.2's config appears to answer.** `[reported]`
arXiv 2603.12201 Table 2: training-free *uniform* interleaving at 1/4 retention drops
Long-Avg to **43.0** against the *searched* pattern's 49.9 and dense DSA's 50.2. GLM-5.2's
pattern is uniform (freq 4, offset 3), not searched. `[reported]` the paper's Table 3
shows the *training-aware* variant — which distils each retained indexer against the
averaged attention of the layers it serves — recovers uniform 1/4 to parity (50.6 vs 51.0).
`[inferred]` GLM-5.2 must have used the training-aware path; a uniform pattern this
aggressive is not viable training-free. This is a good thing to know if anyone proposes
retrofitting IndexShare onto GLM-5.1 weights: **do not**, it needs the training.

### 1.3 The two-batch-overlap tradeoff, precisely

`[verified]` upstream SGLang `python/sglang/srt/server_args.py:5316-5328`
(our fork: `:5053-5063`, identical text) hard-raises when
`enable_two_batch_overlap and index_topk_freq > 1`.

**Why the refusal is technically correct.** TBO splits a batch into two microbatches and
interleaves them so one's communication overlaps the other's compute. `[verified]` the
implementation (`batch_overlap/two_batch_overlap.py`) rewrites the model forward into an
*op-list* form driven by `model_forward_maybe_tbo`. That op path executes layers as a flat
sequence of stages against a `TboForwardBatch`; it has no channel for a per-layer Python
value threaded from layer *i* to layer *i+1*. `prev_topk_indices` is exactly such a value.
Under TBO, a shared layer would find no carried top-k, and — this is the dangerous part —
would then run **sparse attention against garbage or empty indices** rather than falling
back to dense. Hence the error message: "shared layers would run sparse attention without
indices."

**What you give up.** TBO is the standard lever for hiding all-to-all / all-reduce behind
compute at moderate-to-high concurrency. On this box collectives are 19.6% of C1 time.
`[inferred]` the ceiling on what TBO could have recovered is bounded by that share, and at
C1 with two microbatches of half a request each it would recover essentially none of it —
TBO is a throughput lever, not a latency lever. The real loss is at C64+, where the DP
all-gatherv/reduce-scatterv is the thing you would want to hide.

**The four ways out, ranked.**

| option | verdict |
|---|---|
| Set `index_topk_freq = 1` in a copy of `config.json` and lose IndexShare | `[inferred]` **wrong**: the shared layers have no indexer weights in the checkpoint. The model would build 78 indexers, 57 of them uninitialized, and produce garbage. Do not. |
| Teach the TBO op path to thread `prev_topk_indices` | `[inferred]` the correct fix. It is a plumbing change in `two_batch_overlap.py` mirroring what `#30839` did for the CUDA-graph/PD paths. Nobody has done it. Related: SGLang #32529 "[WIP][Spec] Enable Two-Batch Overlap in Draft Models". |
| Use DP-attention + DeepEP instead of TBO for the throughput regime | **what the published recipes actually do.** Every `balanced` / `high-throughput` cookbook cell for GLM-5.2 uses `--dp 8 --enable-dp-attention` (+`--moe-a2a-backend deepep` on FP8). None uses TBO. `[verified]` |
| Accept it at C1 | correct for the latency objective. |

`[verified]` a second, independent TBO block exists: `adaptive_spec_params.py:77-80`
refuses adaptive speculative decoding under TBO ("adaptive state swap would discard the
TboAttnBackend wrapper"). So TBO also costs you adaptive spec even if the DSA block were
lifted.

### 1.4 MoE configuration and routing

`[verified]` from the local config and `deepseek_v2.py`:

- 256 routed experts, top-8, sigmoid scoring, `noaux_tc` bias-corrected routing with a
  per-expert fp32 `e_score_correction_bias [256]`, `norm_topk_prob=true`,
  `routed_scaling_factor=2.5`.
- **`n_group = 1`, `topk_group = 1`.** DeepSeek-V3 constrains a token's experts to
  `topk_group` of `n_group` device groups, bounding all-to-all fan-out. **GLM-5.2 does
  not.** `[inferred]` a token's 8 experts can land on all 8 ranks under EP. This makes EP
  strictly less attractive here than it is for DeepSeek-V3.
- Layers 0-2 are dense MLP at width 12288; layers 3-77 are sparse; `moe_layer_freq = 1`.
- **The shared expert is fused into the routed MoE kernel.** `[verified]`
  `determine_num_fused_shared_experts` (`deepseek_v2.py:2964`) fires when
  `architectures[0] == "GlmMoeDsaForCausalLM"`, `n_routed_experts in (256, 384)` and
  `n_shared_experts == 1`. GLM-5.2 satisfies all three, so the kernel runs **257 experts,
  not 256**. The fusion is silently disabled by `--disable-shared-experts-fusion`, SBO,
  TBO, a DeepEP a2a backend, `moe_ep_size > 1` on CUDA, and W4AFP8/W4A16.
  `[inferred]` **turning on EP or DeepEP changes the MoE kernel's expert count from 257 to
  256 with no log line.** If you A/B TP8 against EP8 and the MoE time does not move the way
  you expect, this is why.
- `[verified]` the FP8 config pins `moe_router_dtype: "float32"`; the NVFP4 config
  **omits the key**. SGLang PR #29892 ("Support GLM-5.2 moe router use FP32") and PR #31213
  ("[GLM-5.2] Keep GlmMoeDsa MoE `e_score_correction_bias` in fp32") both exist, and an
  AMD-side bug #34857 says "Router GEMM output should always be fp32, and the expert
  correction bias should not be cast to bf16". `[unverified]` on our stack — worth 10
  minutes.

### 1.5 The MTP layer

`[verified]` `num_nextn_predict_layers = 1`, checkpoint index **78**. It is **not** a
lightweight EAGLE head. Layer 78 has 1,569 layer tensors — full MLA attention, its own
indexer, its own 256-expert MoE and shared expert — plus four MTP-specific tensors
(`enorm`, `hnorm`, `eh_proj [6144, 12288]`, `shared_head.norm`). It reuses the target's
`embed_tokens` and `lm_head` (`deepseek_v2.py:3105-3115`).

Size: **10.03 GB (FP8) / 19.91 GB (NVFP4)**. `[verified]`

`[reported]` FP8 model card: "We also improve GLM-5.2's MTP layer for speculative decoding,
increasing the acceptance length by up to 20%."

### 1.6 Config fields that will bite you

- `head_dim: 192` **contradicts** `qk_head_dim: 256` and `v_head_dim: 256`. `[verified]`
  A generic consumer computing `num_attention_heads * head_dim = 64 * 192 = 12288` is wrong;
  the true `o_proj` input is `64 * 256 = 16384` (confirmed by the tensor shape
  `[6144, 16384]`). SGLang is immune because MLA reads the component dims directly.
  Note GLM-5/5.1 declare `head_dim: 64` for the same architecture — the field is simply
  not maintained. **Never use it.**
- `num_key_value_heads: 64` is nominal. MLA stores one 576-wide latent per token. A KV
  estimator that believes `64` will be wrong by ~57x.
- `num_experts: 256` in the NVFP4 config duplicates `n_routed_experts`. A parser adding
  `n_shared_experts` gets 257.
- `GLM-5.2-NVFP4/model.safetensors.index.json` advertises `"total_parameters": 380989135104`
  — **wrong by ~2x**, it counts each packed `uint8` as one parameter. `[verified]`
- The FP8 build's `modules_to_not_convert` lists 22 entries named
  `self_attn.indexers_proj`, a module **that does not exist**. The real one is
  `self_attn.indexer.weights_proj` and it is *not* in the list, yet ships BF16 anyway.
  `[verified]` A re-quantization tool that round-trips this config produces a different model.

### 2.3 KV bytes per token

`[verified]` `DSATokenToKVPool` (`memory_pool.py:4289`) allocates two buffers per layer.
`page_size` is asserted to be exactly **64** on CUDA (`memory_pool.py:4347`).

```
MLA latent, FP8 KV (kv_cache_configurator.py:1963-1973):
  kv_lora_rank + kv_lora_rank/128*4 + qk_rope_head_dim*2
= 512 (nope, fp8) + 16 (fp32 per-128 block scales) + 128 (rope, kept BF16)
= 656 B / token / layer

MLA latent, BF16 KV:
  (512 + 64) * 2 = 1152 B / token / layer

Indexer K (memory_pool.py:4358-4383):
  128 + 128/128*4 = 132 B / token / layer
```

MLA has one KV head, so **TP does not shard the KV cache** — every rank holds a full copy.

| configuration | B / token / GPU | GB per 1M tokens / GPU |
|---|---:|---:|
| FP8 KV + indexer allocated on all 78 layers (**what ships**) | 656*78 + 132*78 = **61,464** | 61.46 |
| FP8 KV + indexer only on the 22 real layers | 656*78 + 132*22 = **54,072** | 54.07 |
| BF16 KV + indexer on 78 | 1152*78 + 132*78 = **100,152** | 100.15 |

`[reported]` TensorRT-LLM quotes 55,224 -> 47,700 B/token for the same model. The delta,
7,524 B, is exactly `57 shared layers x 132 B` — independent confirmation of the 132.
Their MLA term (55,224 - 10,296 = 44,928 = 576 x 78) implies TRT-LLM packs the full 576-wide
latent in 576 bytes where SGLang spends 656. `[inferred]` **SGLang's MLA KV layout is 13.9%
larger than TRT-LLM's** for the same precision — the difference is the BF16 rope tail plus
fp32 block scales. Worth confirming before you size a 1M deployment.

**Hardware constants.** B200 SXM HBM3e nominal **8.0 TB/s** per GPU `[unverified]` — I did

Three conclusions, and they are the point of this whole document.

1. **Nothing here is bandwidth-bound.** The best published B200 configuration leaves 41% of
   HBM bandwidth unused; ours leaves 60%. Optimising *bytes* is second-order; optimising
   *kernel efficiency and launch overhead* is first-order. This is consistent with the
   measured hotspot profile — dense GEMM 37.1% at M=1 is a small-M efficiency problem, not
   a traffic problem.
2. **The FP8 build is the worse deal on B200 despite reading fewer bytes** — 26% of roofline
   vs 59%. `[inferred]` DeepGEMM's block-scaled FP8 path at M=1..6 is much further from peak
   than the FlashInfer/TRT-LLM NVFP4 path on SM100. This is the strongest argument for
   staying on the NVFP4 checkpoint.
3. **The NVFP4 build's BF16 attention is 2.7 GB/token/rank of pure waste** that would also
   *improve* the kernel efficiency (FP8 tensor cores instead of BF16). Fixing it moves both
   the numerator and the denominator.

### 3.4 Collectives per token, and the latency floor they imply

Pure TP8, no DP attention. Each decoder layer needs an all-reduce after `o_proj` and one
after the MoE `down_proj`, both on `[M, 6144]`. `[verified]` SGLang defers/fuses them:
`o_proj` is constructed with `reduce_results=False`, and when
`should_fuse_mlp_allreduce_with_next_layer` the MLP all-reduce is folded into the next
layer's norm (`tllm_mnnvl_allreduce::oneshotAllreduceFusionKernel` in the profile).

```
payload of one all-reduce, M=1, BF16 : 6144 * 2                       =   12,288 B
count per decoded token (target only): 2 * 78                         =      156
total payload                        : 156 * 12,288                   = 1.917 MB

ring wire bytes  = 2*(8-1)/8 * payload                                = 3.355 MB
one-shot/NVLS    ~ (7/8)*payload in + payload out                     = 3.594 MB

bandwidth term at 0.9 TB/s/GPU unidirectional: 3.355e6/0.9e12         = 3.7 us
```

Measured collective share at C1: 19.6% of 2.74 ms = **537 us**, i.e. **~3.4 us per
all-reduce**. `[inferred]` **the bandwidth term is ~1% of the observed collective cost.**
The other 99% is per-call fixed cost and rank-arrival skew. 47% of 537 us = **252 us/token
of pure waiting**, which is **9.2% of TPOT**.

Add the speculative path. Under EAGLE `k`-1-`(k+1)`:

```
per verify iteration:
  1 target forward over 78 layers  -> 156 all-reduces
  k draft forwards over 1 layer    ->   2k all-reduces
  k lm_head all-gathers            ->   k  all-gathers of [1, 154880]

lm_head all-gather payload, BF16 : 154880 * 2 = 309,760 B
   -- 25.2x the size of a hidden-state all-reduce, once per draft step
5-1-6: 166 all-reduces + 5 all-gathers = 1.549 MB of all-gather per iteration
       (81% of the entire target forward's all-reduce payload)
```

`[inferred]` **the draft loop's logits all-gather is the single largest collective payload
in the whole iteration.** SGLang PR **#30466**, "[Spec] Distributed argmax for greedy EAGLE
draft over TP (multimem NVLink scatter)", is aimed at exactly this — and the multimem
all-gather it introduces is the code path the reporter of issue #31093 **had to disable** to
get past the draft-graph IMA at all. That is not a coincidence; see §6.4.

**Latency floor, assembled.** `[inferred]` for NVFP4 as shipped, per target forward:

```
weight traffic   8,756 MB / 8.0 TB/s (nominal)          = 1,095 us
                 ... / 6.8 TB/s (85% achievable)        = 1,288 us
collectives      156 x 3.4 us                           =   530 us   <- measurable, mostly fixable
DSA indexer      5.8% of 2.74 ms x AL ...               (workload-dependent, ~0.4 ms/iter)
                                                          --------
irreducible-ish floor per target forward               ~= 1.8 ms
```

With 5 draft steps at ~0.4 ms each, an iteration is ~3.8 ms; at AL 4.6 that is
**TPOT ~0.83 ms, ~1,200 tok/s**. `[inferred]` That is the number to aim at. The published
1.85 ms is 2.2x off it; our 2.74 ms is 3.3x off it.

### 3.5 What the DSA indexer costs, per token

`[inferred]` at context length `S`:

```
per full layer, per query token:
  wq_b GEMM   : 2 * 1 * 4096 * 2048                   =   16.8 MFLOP
  wk GEMM     : 2 * 1 *  128 * 6144                   =    1.6 MFLOP
  logits      : 32 heads * 128 dim * S * 2            =    8192*S FLOP
  top-2048 sel: O(S) with a partial sort

at S = 128K, logits = 1.07 GFLOP per full layer per token
  x 21 full layers                                     = 22.5 GFLOP / token
  x 78 layers if there were no IndexShare               = 83.6 GFLOP / token
```

`[inferred]` The 3.71x ratio at long context is the arithmetic behind the card's claimed
"2.9x reduction in per-token FLOPs at 1M" (the card's figure counts total model FLOPs, not
indexer FLOPs, so it is smaller than 3.71x — consistent).

Measured DSA indexer share at C1 on our short-context workload: **5.8%**. `[inferred]` that
share grows roughly linearly in `S`; at 128K it should dominate. **Re-profile at 128K before
concluding anything about the indexer.**

## 4. Parallelism recommendation

### 4.1 For minimum single-stream latency (the C1 objective)

**TP8, no DP, no EP, no TBO, NVFP4 checkpoint, EAGLE 5-1-6.**

Reasoning:

- **TP8 over EP8.** At M=1 the MoE reads 8 experts. Under TP8 each rank reads 1/8 of each
  of the 8, in one fused kernel covering 257 experts (shared fused in), with a single
  all-reduce. Under EP8 each rank reads whole experts, the shared-expert fusion silently
  turns off, and `n_group=1` means the dispatch can fan out to all 8 ranks. `[inferred]`
  EP adds a dispatch+combine round trip per MoE layer — 150 extra collectives per token —
  to save nothing at M=1. EP is a throughput mechanism.
- **No DP attention.** DP attention replicates attention per DP rank and is a win when there
  are enough independent sequences to fill it. At C1 there is one sequence; DP8 would leave
  7 ranks idle in attention and add a gather. `[verified]` every published `low-latency`
  cookbook cell omits `--dp` / `--enable-dp-attention`; every `balanced`/`high-throughput`
  cell includes them.
- **No TBO.** Refused by the engine (§1.3), and a throughput lever anyway.
- **NVFP4 over FP8** on measured evidence: 59% of roofline vs 26% (§3.3), and 33 GiB/GPU
  more headroom for KV and graphs.
- **Prefill CP is available and single-node only.** `[reported]` cookbook: "Prefill Context
  Parallel is single-machine only (SGLang asserts `tp_size <= 8`)". `attn_cp_size` is
  auto-derived as `tp/dp`. `[reported]` "interleave" is the verified layout; "zigzag" is
  experimental and restricted to batch_size=1. For a C1 long-context TTFT objective, CP8
  with `--cp-strategy interleave` is the lever. `[unverified]` on our box.

### 4.2 For minimum cost per user (the C64 objective)

**TP8 + DP8 attention + EAGLE 2-1-3, NVFP4.** At very high concurrency, drop spec entirely.

`[verified]` the published B200 NVFP4 cells:

- `balanced` (C64-C256): `--tp 8 --dp 8 --enable-dp-attention --quantization modelopt_fp4
  --speculative-num-steps 2 --speculative-eagle-topk 1 --speculative-num-draft-tokens 3
  --chunked-prefill-size 32768 --mem-fraction-static 0.92 --max-running-requests 256`
  with the cookbook's own explanation: *"Shorter draft (MTP 2-1-3) than low-latency's 5-1-6:
  at this concurrency the verify overhead of a long draft outweighs the accept-length gain."*
- `high-throughput` (C1024+): the same minus all speculative flags,
  `--max-running-requests 512`.

`[reported]` measured on B200 NVFP4: C64 TPOT 12.70 ms at 3,770 total-tok/s/GPU; C256
TPOT 30.00 ms at 5,343; C1024 (no spec, 0.5.15) TPOT 117.73 ms at 6,094; C4096 152.78 ms at
5,971. Our 40.8k tok/s at C64 is `[inferred]` ~5,100 total-tok/s/GPU equivalent if you
convert on the same ISL/OSL basis — in the right neighbourhood but on a different workload,
so not directly comparable.

**Note the DeepEP asymmetry.** The FP8 balanced/HT cells use `--moe-a2a-backend deepep`;
the NVFP4 cells do not. `[unverified]` whether DeepEP + `modelopt_fp4` is simply unvalidated
or actively worse. Worth an A/B.

### 4.3 What we should *not* do

- **EP8 on CUDA**, unless you have measured it: it disables shared-expert fusion silently.
- **PP**, on a single node. `[reported]` issue #29162 "GLM-5.2 - pipeline parallel - index
  out of range"; `[reported]` PR #33284 documents a PP+MTP startup failure
  (`DSA MHA indexer did not produce the requested MTP seed`) on TP1/PP7.
- **BF16**: does not fit (§2.1).

ModelOpt's exclusion of layer 78 may have been deliberate draft-quality protection or may
have been an artifact of not recognising the layer. `[unverified]`. The cost of the choice

### 5.4 KV cache format

`[verified]` both builds ship **no** `k_scale`/`v_scale` tensors. The NVFP4 build's
`.quant_summary.txt` shows `k_bmm_quantizer` / `v_bmm_quantizer` as
`(4, 3) bit ... amax=dynamic` — E4M3 with runtime-computed scales.

Recommendation: **FP8 KV**. `[verified]` it is what the checkpoint declares
(`kv_cache_scheme: 8-bit float`), what NVIDIA's own vLLM line uses
(`--kv-cache-dtype fp8_e4m3`), and what SGLang's DSA pool defaults to. It costs 656 vs 1152
B/token/layer — **43% less** — and the AA-LCR long-context-recall number (70.13) was
measured with it. BF16 KV costs you 630 GB per 1M tokens across the node for no published
accuracy benefit.

The one open question is the 656-vs-576 layout gap against TRT-LLM (§2.3).

## 6. Speculative decoding

### 6.1 What ships

`[verified]` one MTP layer, in-checkpoint at index 78, a complete decoder layer with its own
indexer. `[verified]` SGLang selects it by rewriting the architecture string
(`model_config.py:580-581`: `GlmMoeDsaForCausalLM` -> `GlmMoeDsaForCausalLMNextN` when
`is_draft_model`) and defaults `speculative_draft_model_path` to the target path
(`speculative_hook.py:576-578`). There is no separate draft checkpoint to download.

`[verified]` `index_share_for_mtp_iteration: true`. The draft reuses the target's DSA top-k
rather than recomputing the indexer on every draft step. `[reported]` TRT-LLM #15806
describes the same mechanism: "On draft step 0 the per-request last-token top-k is stashed
on the attention metadata; for draft steps > 0 the indexer skips the logits computation and
the top-k selection."

`[verified]` SGLang goes one step further than TRT-LLM: PR #29787 (merged 2026-07-07) moves
the capture from the first *draft-decode* step to the *draft-extend* step, so the seed comes
from the last verified token's target-derived hidden state. It is gated on
`speculative_eagle_topk == 1`, `index_share_for_mtp_iteration=true`, and a valid `index_topk`.

### 6.3 What our number implies

`[inferred]`, and this is the important derivation:

```
TPOT = T_iteration / AL

cookbook B200 NVFP4 5-1-6 with AL pinned at 3.5:
   T_iter = 1.85 ms * 3.5                                  = 6.48 ms

model that as T_target + k * T_draft:
   if T_draft ~ 0.4 ms  ->  T_target ~ 6.48 - 5*0.4        = 4.48 ms

our 3-1-4 on the same hardware and checkpoint:
   T_iter = 4.48 + 3*0.4                                   = 5.68 ms
   observed TPOT 2.74 ms  ->  implied AL = 5.68 / 2.74     = 2.07
```

`[inferred]` **our accept length is around 2.1 out of a maximum of 4.** Published GLM-5.2
gets 4.5-5.2 out of a maximum of 6. Even allowing generous error bars on `T_draft`, our
acceptance is low. **Measure it before anything else** — `/metrics`,
`generation_tokens_total / spec_verify_calls_total`.

Candidate causes, all `[reported]` open issues:

- **#32176** "HiCache loadback 后 GLM-5.2 EAGLE acceptance 静默坍塌" — acceptance silently
  collapses after a HiCache load-back.
- **#32459** "EAGLE speculative decoding defeats radix prefix reuse for multi-turn traffic
  (GLM-DSA NVFP4, v0.5.16) — no crash, silent 97%->40-53% reuse collapse."
- Real data vs the `random` dataset: the cookbook explicitly refuses to publish real
  acceptance on `random` because "random-dataset acceptance is unrealistic".
- Reasoning tokens: `[inferred]` accept length on `<think>` content should be *higher* than
  on prose (it is more predictable), which makes a 2.07 more surprising, not less.

### 6.5 Four things to try, in order

Each is drawn from a published artefact, not invented here.

1. **`--speculative-moe-runner-backend triton`.** `[reported]` SGLang issue #32377 is the
   sibling crash: `tvm.error.InternalError in trtllm_bf16_moe on Blackwell (SM100) during
   speculative decoding (EAGLE) with GLM-5.2-NVFP4`, failing in
   `eagle_worker_v2.py:847 _draft_extend_for_prefill` inside
   `trtllm_batched_gemm_runner.cu:286` on
   `numBatches: 256, GemmMNK: 1 6144 512, Kernel: bmm_Bfloat16_...sm100f`. A maintainer's
   reply: *"can you please set `--speculative-moe-runner-backend=triton`, and see if it fixes
   your issue?"* `[verified]` the flag exists in our fork (`server_args.py:2141`).

   **Why this is the top candidate.** `[verified]` the NVFP4 checkpoint leaves layer 78
   entirely BF16. So the *target* MoE runs an NVFP4 kernel and the *draft* MoE runs
   `trtllm_bf16_moe` — a 256-batch BF16 batched GEMM at M=1..6 — which is the exact kernel
   in #32377's stack trace. Longer drafts mean more calls into it per iteration. This is a
   clean mechanistic story for "3-1-4 survives, 5-1-6 does not".

2. **Bound the draft graph.** `[verified]` the published B300 and GB300 NVFP4 low-latency
   cells carry three flags the B200 cell does **not**:
   `--max-running-requests 16 --cuda-graph-max-bs 16 --max-prefill-tokens 8192`.
   `[inferred]` these cap how many draft-decode capture buckets exist and how large the
   biggest one is. The crash is *in capture*. Adding them to the B200 config is cheap and
   directly targets the failing phase. (The #31093 reporter used
   `--cuda-graph-max-bs-decode 48` — 3x larger.)

3. **Disable the multimem logits all-gather.** As the reporter did. `[verified]`
   `logits_processor.py:384` in our fork. This is the collective identified in §3.4 as the
   largest payload in the draft loop and the subject of PR #30466. If disabling it fixes the
   capture, the bug is in that path and PR #30466 is where to look.

4. **Bisect to `430418e2` (2026-07-03).** `[reported]` the last known-good commit, available
   as image `lmsysorg/sglang:dev-glm52-nvfp4`. `[reported]` NVIDIA's own model card also
   names an image, `lmsysorg/sglang:dev-glm52-nvfp4` — the same one. That is a strong hint
   that the vendor's published NVFP4 numbers were taken on that build.

`[inferred]` if all four fail, **4-1-5 is the fallback, not 3-1-4** — it is strictly closer
to the published shape, and if the failure scales with draft length it may sit under the
threshold.

### 6.6 Reasoning behaviour, TTFT vs TTFAT

**How effort is set — ground truth from the shipped chat template.** `[verified]`
`chat_template.jinja` (md5 `42994f78b64752fe472149dd7e20410d`, identical in both builds),
lines 2-3 and 118:

```jinja
{%- set effective_reasoning_effort = 'high' if reasoning_effort is defined
      and reasoning_effort == 'high' else 'max' -%}
{%- if (enable_thinking is not defined or enable_thinking)
      and effective_reasoning_effort is not none -%}
  <|system|>Reasoning Effort: {{ effective_reasoning_effort | capitalize }}
{%- endif -%}
...
<|assistant|>{{- '<think></think>' if (enable_thinking is defined and not enable_thinking)
                 else '<think>' -}}
```

Consequences, all `[verified]` from that template:

1. **The default is `max`.** Unset `reasoning_effort` -> `max`.
2. **`'high'` is the only alternative.** `"low"`, `"medium"`, `"none"`, `"minimal"`, and
   every typo fall through the `else` and become **`max`**. There is no low-effort mode via
   this parameter. `[inferred]` this is a live footgun: SGLang PR #31477's own accuracy run
   states `reasoning_effort=none`, which per this template ran at **max**.
3. **Thinking is turned off by `enable_thinking=false`**, which drops the system line *and*
   prefills the assistant turn with an empty `<think></think>`. `[reported]`
   `github.com/zai-org/GLM-5` README confirms: `reasoning_effort` "max" (default) / "high";
   "Thinking can be turned off entirely by setting `enable_thinking=false`."
4. The mechanism is **prompt conditioning**, not a token or a config switch. There is no
   engine-side lever, no logit bias, no separate weights. Nothing in the serving stack can
   shorten the reasoning except the prompt.
5. `[reported]` the Z.ai API exposes it as a `thinking: {type: "enabled"|"disabled"}` object
   *and* a separate `reasoning_effort` string.

**Why this dominates every latency metric.**

`[reported]` Z.ai's own benchmark footnotes: HLE at max generation length **163,840
tokens**; SWE-Bench Pro at `max_new_tokens=32k`; NL2Repo 48k; ProgramBench
`max_tokens=64000, reasoning_effort=max`; FrontierSWE / PostTrainBench / SWE-Marathon all at
"1M context length, max effort level, and 128K maximum output tokens". These are not
chat-length generations.

`[reported]` SGLang's own AIME25 accuracy command uses `--max-tokens 64000 --thinking`.

**TTFT vs TTFAT.** `[reported]` Artificial Analysis distinguishes:

- **TTFT** — time to the first token of any kind. For GLM-5.2 that is the first `<think>`
  content token.
- **TTFAT (Time to First Answer Token)** — "Accounts for reasoning model 'thinking' time",
  i.e. time until the first token *after* `</think>`.

`[reported]` AA's listing for "GLM-5.2 (max)": 138.7 output tok/s, TTFT 1.37 s, TTFAT
1.37 s median across providers, Intelligence Index 53 (#4 of 106), $1.40/M in, $4.40/M out,
$0.32 per task, ~1 minute weighted average time per task, 140M output tokens generated
during evaluation, 1M context, 753B/40B. `[unverified]` — the TTFT and TTFAT being
*identical* is almost certainly a rendering artifact of the summary I fetched; for a
max-effort reasoning model TTFAT must be much larger. **Do not quote the 1.37 s TTFAT
without re-reading the page.**

**What this means for us.** `[inferred]`

- Our TTFT of 189 ms is the time to the first *thinking* token. The user-visible latency is
  TTFAT = `TTFT + (reasoning tokens) x TPOT`. At a modest 2,000 reasoning tokens and 2.74 ms
  TPOT, TTFAT = 189 ms + 5.48 s = **5.7 s**. At AA's ~1 min/task weighted average, reasoning
  is essentially the entire user-perceived latency.
- **Therefore TPOT, not TTFT, is the number that moves TTFAT.** A 2x TPOT improvement halves
  the wait for the answer; a 2x TTFT improvement changes it by 3%.
- **Leaderboard distortion:** any tok/s figure that counts thinking tokens is inflated
  relative to useful output. `[reported]` the vLLM recipe page says exactly this: *"Pure
  throughput benchmarks tend to under-report real speed"* because of MTP acceptance; the
  converse also holds — throughput over-reports *value* when most tokens are thinking.
  When we publish a number, state (a) whether thinking was on, (b) which `reasoning_effort`,
  (c) whether tok/s counts thinking tokens, and (d) TTFAT alongside TTFT.
- `--reasoning-parser glm45` is what splits the two streams. `[verified]` present in our
  fork (`reasoning_parser.py:1612`, `Glm45Detector`) and in every published recipe.
- **Benchmarking implication:** the cookbook's ISL 8192 / OSL 1024 workload generates 1024
  tokens, which for a max-effort model is *entirely* thinking and never reaches an answer.
  Its TPOT is a valid decode-speed measurement and a meaningless TTFAT measurement.

**What a like-for-like comparison would require.** `[inferred]` The "~500 tok/s GLM-5 FP8 on
8xB200" number is **not** comparable to our 365 tok/s, for five independent reasons:

1. **Different model.** GLM-5, not GLM-5.2. Same 78x6144x256 shape, but **78 indexers
   instead of 21** — GLM-5 does *more* indexer work per token, so TileRT's number is if
   anything harder to hit. Offsetting that, GLM-5's context is 202,752 not 1,048,576, and
   its RoPE theta is 1e6 not 8e6 — irrelevant to decode speed.
2. **Different precision.** GLM-5-**FP8**, not NVFP4. Per §3.2 the FP8 roofline is *higher*
   (1,199 vs 914 tok/s) but the measured SGLang FP8 path is much *further* from it.
3. **Different runtime shape.** TileRT is a compiler-driven, tile-scheduled, single-model,
   single-process runtime with pre-sharded per-device weights (`*_dev_{0..7}` keys). It is
   not a server: the README's examples are `generator.generate(prompt)` in a Python process.
   There is no continuous batching, no radix cache, no scheduler.
4. **Different acceptance accounting.** TileRT's chart bars are labelled "at average
   acceptance length 3.2" and "best-case 4.0". Our 365 is real-data acceptance at 3-1-4.
5. **Different environment.** `[verified]` TileRT v0.1.5 hard-pins `torch==2.11.0+cu130`,
   `transformers==4.46.3`, Python 3.12, CUDA 13.2. We are on CUDA 13.2 — compatible — but
   `transformers 4.46.3` is five major versions behind what GLM-5.2's config declares
   (`transformers_version: "5.11.0"`), which is itself a signal that TileRT never parsed a
   GLM-5.2 config.

**To make the comparison honestly** you would have to: download `zai-org/GLM-5-FP8` (a
second ~750 GB), run `weight_converter --model_type glm-5`, run TileRT's own
`tilert.generate --with-mtp` benchmark mode, and then run SGLang on the *same* GLM-5-FP8
checkpoint at 8xB200 TP8. That is the only apples-to-apples framing, and it measures
GLM-5, which is not the model we serve.

`[inferred]` **Not worth doing.** What *is* worth extracting from TileRT is the claim
structure: 500 tok/s on a 744B FP8 model at 8xB200 is `1/500 = 2.0 ms`/token, against our
NVFP4 roofline floor of 1.095 ms and our published-best 1.85 ms. TileRT is not
order-of-magnitude ahead of a well-configured SGLang on this class of model; it is roughly
at the published 5-1-6 SGLang number. The gap we should close is the one to *our own
stack's* published configuration, not the one to TileRT.

## 9. Open questions and what to measure on our box

Ordered by expected value. Each has a concrete measurement.

### Tier 1 — do this week

1. **What is our actual accept length?** `/metrics`,
   `generation_tokens_total / spec_verify_calls_total`, on real traffic, at 3-1-4.
   §6.3 predicts ~2.1; published 5-1-6 gets 4.6. If we are at 2.1, the model is
   under-drafting and the crash is not the only problem.
2. **Does `--speculative-moe-runner-backend triton` unblock 5-1-6?** One flag, one restart.
   Mechanism in §6.5.1. If yes, this is a >1.4x TPOT win.
3. **Do `--max-running-requests 16 --cuda-graph-max-bs 16 --max-prefill-tokens 8192`
   unblock 5-1-6?** The published B300/GB300 cells carry them; the B200 cell does not.
4. **Is `SGLANG_NVFP4_CKPT_FP8_GEMM_IN_ATTN` on?** Log the resolved quant config per module
   at startup. If off, turn it on and re-measure the 37.1% dense-GEMM share. Expected: -3.7%
   of decode bytes, plus whatever the FP8-vs-BF16 tensor-core difference is worth at M=1.
5. **What does the pool actually allocate per token?** Log `token_to_kv_pool` sizes at
   startup and compare against 61,464 B/token. If it matches, PR #30531's 7,392 B/token is
   ours to take.
6. **What is our real HBM bandwidth?** Every ceiling in §3 assumes 8.0 TB/s nominal. Measure
   it. A 15% error there moves every conclusion.

### Tier 2 — the structural wins

7. **Requantize `fused_qkv_a_proj_with_mqa` and `o_proj` to FP8 block-128.** 2,238 MB/token/rank,
   25.6% of decode traffic. Both are straightforward: the FP8 checkpoint already has the
   tensors in exactly the right format — this is a *mixed load* from two checkpoints, not a
   new quantization run. `[inferred]` **This may be the single most valuable engineering
   item on the page**, and it is unusual: we own both builds, and the pieces we want from
   each are disjoint.
8. **Skip building indexers on the 57 shared layers** (SGLang #30922). ~1.07 GB/GPU BF16.
9. **Skip the indexer KV for shared layers** (SGLang #30531; TRT-LLM #16558 shipped it).
   +13.7% KV capacity by our arithmetic, +15.8% by theirs.
10. **Attack the 252 us/token of rank-arrival skew.** Try SGLang #34134 (CuTe DSL allreduce
    fusion tuned for GLM-5.2). Instrument per-rank arrival times at the layer barrier —
    if one rank is consistently late, it is a placement or NUMA problem, not a collective
    problem. We have 2 NUMA nodes; check the rank-to-NUMA map.

### Tier 3 — things we do not know

11. **Is `moe_router_dtype` fp32 on the NVFP4 path?** The key is absent from that config.
    If SGLang defaults to BF16 there, the two builds route in different precision and it
    shows up nowhere but as divergence. Related: #31213, #34857.
12. **Is our MLA KV layout 13.9% larger than it needs to be?** SGLang 656 vs TRT-LLM 576
    B/token/layer (§2.3). Find out whether the BF16 rope tail is required or historical.
13. **What does the DSA indexer cost at 128K?** Our 5.8% was measured on a short workload.
    §3.5 says it scales with `S`. Re-profile at 8K / 32K / 128K / 512K.
14. **Does DeepEP help or hurt the NVFP4 balanced cell?** The published FP8 balanced cell
    uses it; the NVFP4 one does not. Nobody says why.
15. **Does prefill CP (`--enable-prefill-cp --cp-strategy interleave --attn-cp-size 8`)
    reduce our 189 ms TTFT, and by how much at what context?** Single-node only,
    `tp_size <= 8`, incompatible with DP attention today.
16. **Does EAGLE cost us radix prefix reuse?** Issue #32459 claims a silent 97% -> 40-53%
    collapse for multi-turn traffic on exactly GLM-DSA NVFP4. Measure cache hit rate with
    and without spec on a multi-turn trace.
17. **What is our real TTFAT?** Instrument the `</think>` boundary. Report TTFT, TTFAT,
    thinking-token count and answer-token count separately in every benchmark from now on.
18. **What is our accept length at `reasoning_effort: high` vs default `max`?** Reasoning
    volume changes both the token mix and the acceptance rate. Nobody has published this.
19. **`glm-kernels/` is empty.** `[verified]` Given §3.3 says we are at 40% of roofline and
    the bottleneck is small-M kernel efficiency, the first hand-written kernel should
    probably be a fused `fused_qkv_a_proj_with_mqa` + norm + RoPE at M in {1..6} — the
    replicated 28.7% of decode traffic — not an attention kernel.
